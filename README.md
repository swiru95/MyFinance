# MyFinance — Budget & Portfolio Tracker

A self-hosted, Docker-based application to track the value of your assets over time.
Assets are entered in their native currency (PLN / EUR / USD / CHF), in **grams for gold**,
or as **coin quantity for crypto (BTC, SOL)**, and everything is recalculated into a
single **base currency** you choose. Every update records a timestamp, so you can watch
your portfolio progress on a time chart.

## Features
- **8 asset types out of the box**: Cash, Gold (grams), Stocks, TFI Funds, National Bonds,
  Watches, Bitcoin, Solana, Savings.
- **Multi-currency input** — enter any position in PLN, EUR, USD or CHF.
- **Live prices** — gold per gram, BTC/SOL, and FX rates are fetched from public APIs,
  with static fallbacks so the app keeps working offline.
- **Configurable base currency** (PLN / EUR / USD / CHF); all values are recalculated.
- **Timestamped updates** — every change to a position is stored, powering the history and
  the portfolio-over-time chart.
- **Charts** — line chart of total value over time + allocation donut chart.
- **Effective spend** — what a month really cost, read off the portfolio rather
  than typed in: income minus the change in total portfolio value.
- **Wallet assessment** — a written review of the portfolio against a style you
  pick, generated by a language model running on your own hardware.
- **English and Polish** throughout, including the seeded asset and class names.
- **Entra ID SSO** — OAuth 2.0 authorization code + PKCE, no client secret anywhere;
  access is gated on an app role, not merely on tenant membership.
- **Docker** — one `docker compose up` to run the whole stack. Python runs in a venv.

## Quick start
```bash
docker compose up --build
```
Then open:
- Frontend: http://localhost:3000
- Backend API: http://localhost:8000/docs (interactive OpenAPI docs)

> **Note:** `docker compose up --build` will take a couple of minutes the first time
> (it downloads and builds both images).

## Using the app
1. Go to **Settings** and pick your base currency.
2. Open **Positions** and click **+ Add** on any asset:
   - Currency assets → enter amount + currency.
   - Gold → enter grams (price/gram is fetched live).
   - Bitcoin / Solana → enter coin quantity (price/coin is fetched live).
3. To change a value, click **Update** on that asset's card — a new timestamped entry is
   recorded. Click **History** to see the full timeline for that asset.
4. The **Dashboard** shows the total, live prices, the value-over-time chart and the
   allocation breakdown.

## Effective spend

The **Monthly** page records what you earned and what you think you spent, but
the figure that is hard to argue with is derived instead of typed:

```
effective spend = income − (portfolio value at month end − at month start)
```

Everything you earn either ends up in the portfolio or has been spent, so this
catches spending that never got entered as an expense. The opening balance is
the *previous* month's closing value, and a month still running is measured up
to today.

Two things it deliberately does not do. It shows nothing rather than a guess
when there is no income recorded or no portfolio snapshot on one end of the
month — an unknown opening balance would otherwise read as "you spent your
whole income". And because it is driven by portfolio *value*, a market drawdown
counts towards it exactly as real spending does: a month where crypto fell
6 500 will show 6 500 of extra "spend". That is the honest reading of the
identity, not a bug, and the page says so under the chart.

## Wallet assessment

The **Report** page asks a local language model to review the portfolio and
write it up: what stands out, the risks, and ordered recommendations. You pick
the style it judges against — safe, balanced, risky or long-term — and the same
holdings get read very differently depending on which you choose.

Nothing leaves the network. The request goes to `llama-server` on the GPU box,
and the figures it is given are the same ones the dashboard shows.

Two models, for two different jobs:

| Step | Model | Why |
|---|---|---|
| Writes the assessment | `Thinker` (Qwen3.5 122B) | Reasons over the figures; always writes in English, where it is strongest |
| Translates to Polish | `Bielik` (11B) | Polish-native, and far better at it than asking the author model to write Polish directly |

So a Polish report is written in English first and then translated, rather than
being composed in Polish. The report page says so while it is working.

### Configuring it

| Variable | Default | Meaning |
|---|---|---|
| `MYFINANCE_LLM_BASE_URL` | *(empty)* | e.g. `https://llama.kscsc.local:8443`. Empty disables the feature |
| `MYFINANCE_LLM_API_KEY` | *(empty)* | Bearer token. Not needed when a client certificate is configured |
| `MYFINANCE_LLM_MODEL` | `Thinker` | Writes the assessment |
| `MYFINANCE_LLM_TRANSLATE_MODEL` | `Bielik` | Translates into Polish |
| `MYFINANCE_LLM_CA_BUNDLE` | *(empty)* | PEM bundle used to verify the server. **Must contain the intermediate** — see below |
| `MYFINANCE_LLM_VERIFY_TLS` | `false` | Only consulted when no CA bundle is given |
| `MYFINANCE_LLM_CLIENT_CERT` | *(empty)* | Client certificate, for mutual TLS |
| `MYFINANCE_LLM_CLIENT_KEY` | *(empty)* | Its private key |
| `MYFINANCE_LLM_TIMEOUT` | `900` | Seconds. A cold start loads ~76 GB before the first token |

The feature switches itself off unless `BASE_URL` is set **and** there is a
credential — either an API key or a client certificate. The Report page then
says so rather than failing on every attempt.

### Verifying the server's certificate

`llama-server` presents a certificate from the lab's own CA. Verification needs
that CA in a bundle — and the bundle **must include the intermediate, not just
the root**:

> The KSCSC root carries no `keyUsage` extension. Python 3.13 enables
> `VERIFY_X509_STRICT` by default, and strict verification rejects a CA
> certificate that lacks one:
>
> ```
> CA cert does not include key usage extension
> ```
>
> With only the root in the bundle it has to serve as the trust anchor, and
> verification fails. Add the intermediate and *it* becomes the anchor — it does
> carry `keyUsage`, the root is never examined, and strict verification passes
> without being weakened.

That is why other consumers of this server run with verification disabled; they
do not have to. The Helm chart assembles the correct bundle itself
(`templates/configmap-llm-ca.yaml`).

### Mutual TLS

In the cluster the backend pod already holds an autocert-issued identity for
its mutual-TLS connection to PostgreSQL, and that certificate carries
`clientAuth` in its extended key usage. The same pair authenticates it to
`llama-server`, so the pod proves who it is with a certificate instead of
holding a copy of a shared bearer token:

```
CN=myfinance-app.myfinance.svc.cluster.local
```

Nothing extra is mounted and no second certificate is issued — the chart just
points `MYFINANCE_LLM_CLIENT_CERT`/`_KEY` at the files autocert already writes.
The SSL context is rebuilt per request so an autocert renewal is picked up
without restarting the pod.

Setting this is safe before the server asks for a client certificate: a server
that does not request one never sees it.

**The API key is still required.** A certificate authenticates this backend to
the llama-server *router*, but the router does not forward that identity to the
model child process it proxies inference to — so a certificate alone reaches
`/slots` and not `/v1/chat/completions`, which answers `401 Invalid API Key`.
Measured 2026-09-17 against the live server.

The certificate is not decorative, though: where both are presented **the router
authorizes on the certificate**, verified by `/slots` returning `403 insufficient
permissions` even when an admin-scoped key is sent alongside. So the certificate
is what caps this backend's privileges, and the key it carries should be scoped
to the same least-privilege role (`service`, i.e. `INFER` only) rather than
being a shared admin key.

```bash
export MYFINANCE_LLM_BASE_URL=https://llama.kscsc.local:8443
export MYFINANCE_LLM_API_KEY=...          # never commit this
docker compose up --build
```

> **Generation is slow on purpose.** The model router keeps one model resident
> at a time, so the first request after a switch waits for the whole model to be
> paged in — minutes, not seconds. The POST therefore returns a `pending` row
> immediately and generation continues on a worker thread; the page polls it.
> Nothing holds an HTTP request open for the duration, which is what would
> otherwise hit the gateway's 60s timeout.

## Entra ID SSO

Sign-in is Microsoft Entra ID, using the OAuth 2.0 **authorization code flow with
PKCE**. The browser is a public client — there is no client secret anywhere in this
repository, in the chart, or in the image. The backend validates the resulting
access token on every request against the tenant's published signing keys.

```
browser ──1── /api/auth/config ────────────────▶ backend   (tenant + client id, public)
        ──2── authorize?…code_challenge=S256 ──▶ Entra
        ◀─3── ?code=… ──────────────────────────
        ──4── code + code_verifier ────────────▶ Entra
        ◀─5── access token ────────────────────
        ──6── Authorization: Bearer … ─────────▶ backend   (signature, iss, aud, tid, role)
```

**One app registration plays both parts.** It carries the SPA redirect URI *and*
exposes the scope the SPA asks for, so there is a single client id to configure
rather than a client/API pair to keep in sync.

In the kscsc cluster this reuses the app registration that previously served
Actual Budget, which was uninstalled on 2026-09-18. See "Repurposing the Actual
Budget registration" below for what still has to change on it.

### Creating the app registration

In **Entra admin centre → App registrations → New registration**. Name it
`MyFinance`, single tenant, and create it with no redirect URI; the rest is done
on the blades below.

| Blade | What to set |
|---|---|
| **Authentication** | Add a platform → **Single-page application** → `https://myfinance.kscsc.local`. Add `http://localhost:3000` too if you want the flow locally |
| **Expose an API** | Accept the default Application ID URI `api://<clientId>`, then **Add a scope** named `access_as_user`, consent **Admins only**, state **Enabled** |
| **Manifest** | Set `requestedAccessTokenVersion` to `2` — see the trap below |
| **App roles** | **Create app role** → display name `MyFinance User`, member types **Users/Groups**, value `MyFinance.User`, enabled |
| **API permissions** | Add a permission → **My APIs** → MyFinance → `access_as_user`, then **Grant admin consent** |

> **Pick "Single-page application", not "Web".** The Web platform is for
> confidential clients and expects a client secret; the SPA platform is what
> enables PKCE with no secret and sets the CORS headers the token endpoint needs.
> Choosing Web here produces `AADSTS9002326` on redemption, which does not read
> like a platform mistake.

Then, in **Enterprise applications → MyFinance**:

- **Properties → Assignment required → Yes.** Without this, every account in the
  tenant can sign in, and the app role becomes advisory rather than a gate.
- **Users and groups → Add user** — assign yourself the `MyFinance User` role.

That assignment is the actual authorization. A valid token from the right tenant
without the role is rejected with `403`, not `401`, because the caller has proved
who they are and sending them back through sign-in would achieve nothing.

> **The `requestedAccessTokenVersion` trap.** A new registration ships with this
> field set to `null`, which means **v1** — and a v1 access token is issued by
> `https://sts.windows.net/<tid>/`, not by the v2.0 endpoint the sign-in went
> through. The backend accepts both issuers so the API works either way rather
> than rejecting every token with an issuer mismatch that looks nothing like a
> configuration problem. Setting it to `2` is still correct; the leniency is a
> safety net, not a licence to skip the step.

### Repurposing the Actual Budget registration

MyFinance took over Actual Budget's app registration rather than claiming a new
one. Reusing the client id saves only the "New registration" click — a
registration built for confidential-client OIDC sign-in carries none of the SPA
redirect URI, exposed scope, app role or `requestedAccessTokenVersion: 2` that
the table above adds.

With Actual Budget gone, finish the job on the registration:

- Rename it to **MyFinance**.
- Remove the **Web** platform redirect URI — MyFinance uses the SPA platform.
- **Delete the client secret.** It was Actual Budget's, nothing consumes it now,
  and a public client has no use for one. A secret that no longer has a consumer
  is one nobody rotates and nobody notices leaking.

While the registration was still shared, one subtlety was load-bearing and is
worth keeping in mind if you ever share one again: **"Assignment required" is
registration-wide**, so gating one app on it gates every app on that
registration.

### Configuring it

| Variable | Default | Meaning |
|---|---|---|
| `MYFINANCE_AUTH_TENANT_ID` | *(empty)* | Directory (tenant) ID. Empty disables authentication |
| `MYFINANCE_AUTH_CLIENT_ID` | *(empty)* | Application (client) ID. Empty disables authentication |
| `MYFINANCE_AUTH_API_SCOPE` | `access_as_user` | Scope name exposed on `api://<clientId>` |
| `MYFINANCE_AUTH_REQUIRED_ROLE` | `MyFinance.User` | App role the caller must hold. Empty admits anyone in the tenant |
| `MYFINANCE_AUTH_JWKS_CACHE_SECONDS` | `3600` | How long signing keys are cached |
| `MYFINANCE_AUTH_LEEWAY_SECONDS` | `60` | Clock skew tolerated on `exp`/`nbf` |

**Unset tenant or client id disables authentication entirely** — every endpoint
is open and the frontend skips the sign-in screen, the same way an unset LLM base
URL disables the assessment. That is what keeps `docker compose up` working
untouched, and it is why the backend logs

```
AUTHENTICATION IS DISABLED - MYFINANCE_AUTH_TENANT_ID and
MYFINANCE_AUTH_CLIENT_ID are not both set. Every API endpoint is open.
```

at startup. A half-finished deploy looks exactly like local development, and that
line is the only thing that tells them apart.

In the cluster the chart sets both from `auth.tenantId` / `auth.clientId` and
**refuses to render** when `auth.enabled` is true and either is missing, so the
failure lands at `helm upgrade` rather than on a running, open deployment.

### What the backend checks

Every `/api/*` endpoint except `/api/health` and `/api/auth/config` requires a
bearer token. The guard is applied to the whole router list in `src/main.py`
rather than endpoint by endpoint, so a new router is protected by being added to
that list and there is no decorator to forget.

On each request: RS256 signature against the tenant's JWKS, `aud` is this
application, `iss` is this tenant, `tid` is this tenant (a guest account carries a
foreign `tid` behind a familiar issuer), `exp`/`nbf` are current, `scp` contains
the API scope, and `roles` contains the required role.

The `scp` check is what makes this an *access token for this API* rather than
merely a token with the right audience. It matters because an **ID token from the
same app registration is otherwise indistinguishable**: same `aud`, same `iss`,
same `tid`, and it carries `roles` too once the user is assigned one. Entra sets
`scp` on delegated access tokens and never on ID tokens, so that one claim is the
difference between an API credential and a sign-in receipt.

That was not hypothetical here: this registration previously served Actual
Budget, which received ID tokens for the same client id. Without the `scp` check
one of those would have been a working MyFinance credential. The check stays
because it is correct regardless of whether a registration is shared.

Two endpoints are deliberately open:

- `/api/health` — the kubelet's probes call it and carry no credential. It reveals
  nothing beyond "the process is up".
- `/api/auth/config` — it is what the browser reads *before* it has a token, to
  find out which tenant to sign in against.

`GET /api/auth/me` returns the caller as the API sees them, which is the quickest
way to confirm a deployment is really validating tokens rather than waving them
through.

### Sessions

MSAL caches in `sessionStorage`, so closing the tab ends the session. The refresh
token lives there too, which means `acquireTokenSilent` renews the access token
without a redirect and without third-party cookies — the usual reason people
reach for `localStorage` does not apply here.

### When it goes wrong

| Symptom | Cause |
|---|---|
| `AADSTS50011` redirect URI mismatch | The SPA redirect URI must match the origin exactly — scheme, host, port, no trailing slash |
| `AADSTS9002326` cross-origin token redemption | The platform is registered as **Web** instead of **Single-page application** |
| `AADSTS65001` consent required | Grant admin consent for `access_as_user` under API permissions |
| `403 Account is not assigned the MyFinance.User role` | Assign the role under Enterprise applications → Users and groups |
| `401 Token was not issued by the configured tenant` | `tid` or `iss` mismatch — usually the wrong tenant id in values |
| `401 Token is not an access token for this API` | An ID token was sent instead of an access token, or the scope name does not match `auth.apiScope` |
| `503 Cannot reach the identity provider's signing keys` | The backend cannot reach `login.microsoftonline.com`. This is the service failing, not the caller, which is why it is not a `401` |

## Architecture
| Service   | Tech                                        | Port |
|-----------|---------------------------------------------|------|
| frontend  | Next.js 14 (Pages Router), TypeScript, Tailwind, Recharts | 3000 |
| backend   | Python 3.11, FastAPI, SQLAlchemy, SQLite (in a venv) | 8000 |

- The frontend proxies `/api/*` to the backend, so no CORS issues in the browser.
- Reports live in their own table; the snapshot the model was given is stored
  next to the text, because an assessment read six months later is only
  interpretable alongside the figures that produced it.
- SQLite data is persisted in the `myfinance-data` Docker volume.

### Price sources (with offline fallbacks)
- FX: `open.er-api.com`
- Gold: `gold-api.com` (XAU)
- Crypto: CoinGecko (`bitcoin`, `solana`)

Prices are cached in-process for 5 minutes to stay within free-tier rate limits.

## Kubernetes

The cluster deployment lives in the `kscsc-helm-charts` repository as the `myfinance`
chart. Pushing to `main` builds both images and publishes them to GHCR tagged with the
commit SHA; deploying is then a values change:

```bash
helm upgrade --install myfinance ./myfinance -n myfinance --create-namespace \
  -f ./config/values/myfinance__myfinance.yaml \
  --set backend.image.tag=<sha> --set frontend.image.tag=<sha>
```

One caveat worth knowing before changing the frontend: **`next build` bakes the
`next.config.js` rewrite destination into `.next/routes-manifest.json`**, so
`BACKEND_ORIGIN` only has an effect at build time. It works under docker compose because
the backend is literally reachable as the host `backend`. In the cluster the gateway
routes `/api/*` to the backend Service instead, and the chart does not set the variable
at all. If you change `BASE` in `frontend/src/lib/api.ts`, change `gateway.apiPathPrefix`
in the chart to match.

## Local (non-Docker) development
```bash
# Backend
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn src.main:app --reload --port 8000

# Frontend (separate terminal)
cd frontend
npm install
npm run dev
```
Point the frontend at the backend by running it on port 3000 with the backend on 8000
(the `/api` rewrite targets `http://backend:8000`; for local dev without Docker, edit
`frontend/next.config.js` to `http://localhost:8000`).

## Resetting data
```bash
docker compose down -v   # removes the data volume
```
